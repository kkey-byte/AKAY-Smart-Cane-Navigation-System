# GPS source audit — 21 October 2026

## Conclusion and evidence

**The caregiver Track map uses the navigator's phone-derived breadcrumb location. It does not select smart-cane coordinates.** The authorized-data/pairing screen separately displays phone GPS and available cane coordinates. An authenticated cane-telemetry ingestion path exists in backend source, but physical sensor collection and delivery have not been demonstrated.

This is verified by inspecting current Flutter implementation, platform permissions, actual backend location handlers and relevant tests. “Phone GPS” means the location reported by the phone/browser operating-system location provider through Geolocator; source does not prove that each fix came exclusively from satellite GNSS rather than another OS positioning method. A reverse-geocoded address, map tile, planned route or destination pin is not a measured navigator location.

I used the AKAY navigation-tracking workflow. Some comments in that skill and source still mention legacy `live_location/{deviceID}`. The executing implementation uses the paths below. No tracking implementation, source-selection policy, configuration, database or hardware was changed in this audit.

## Recording, freshness and fallbacks

- Phone collection starts when Track is mounted; **sharing the current position through the caregiver path requires breadcrumb recording**, either a walking-track action or navigation start. `_persistNavigationStart` attempts breadcrumb recording and separately starts the legacy SQL session. A failure in one does not establish success in the other. Simply carrying/claiming a cane, logging in or viewing a local phone pin does not prove a shared recording exists.
- `shouldRecordBreadcrumb` rejects invalid coordinates, accuracy over 50m, fixes older than 45s or more than 30s ahead, duplicate/out-of-order timestamps and small jitter. It accepts movement of at least 5m after 2s, or a new timestamp after 20s when stationary. Configured Android stream interval is 2s; actual OS delivery is not guaranteed. Recording enables the Android foreground notification/wake lock or Apple background settings, but background/terminated-app behavior was not device-tested.
- Outbox synchronization runs at recording start, every 10s and on reconnect. Failed uploads retain points locally for retry. Caregiver HTTP watchers poll every 5s. This is periodic synchronization, not direct phone-to-caregiver streaming or a guaranteed update interval.
- `BreadcrumbTrip.isFresh` requires a recording trip with a recent point: no older than 45s and no more than 30s ahead. Track additionally requires the viewer's RTDB connection flag and refreshes age state every 15s. “Recording track”/online therefore indicates recent phone-track data and viewer connectivity, **not cane connectivity**. Saved/completed/interrupted tracks remain historical even with a recent point.
- A stale recording displays “Last known location”; a completed/interrupted trip displays “Saved track”. A trip/API permission or network error removes the affected map position and shows unavailable status. The data card hides old readings on snapshot errors/access revocation. Missing coordinates remain unavailable.
- `CaneReading.fresh` also uses a 45s window; the data card ticks every 5s. Older stored coordinates/battery/status remain visible alongside a stale/unavailable label. There is no demonstrated BLE disconnect callback, heartbeat or authoritative online/offline event. A fresh status reading with no coordinates still means “Cane GPS unavailable”.
- Map default center and the `(0,0)` sentinel in `NavigatorLocationService.location`/`selfNavigator` are UI/data defaults, **not tracking measurements**. The normal caregiver marker requires a recorded-point timestamp. Planned route polylines and pins are not substituted for GPS. Geocoding failure falls back to a coordinate label without changing its coordinates.

## Disconnects and permission denial

**Cane disconnected:** no automatic source transition exists. Phone recording continues if phone location, recording and connectivity permit; cane data eventually becomes stale or is unavailable. The main caregiver map remains phone-based whether a cane is connected or not. Source does not prove autonomous cane transmission, offline cane buffering or a reconnect protocol. Device-authenticated payloads alone do not prove that coordinates originated in a physical GNSS receiver.

**Navigator phone location off/denied:** `_ensurePermission` checks system services, requests denied permissions, and returns explicit denied/permanently-denied messages. An initial phone fix/recording cannot start without permission and a usable accurate fix. Device telemetry, if independently delivered, is not controlled by phone location permission, but the Track map does not switch to it. While recording, a failed stream stops delivering new fixes; old breadcrumb points age out of live status. Existing `livePosition/lastPosition` are not automatically cleared on every error, so the navigator's local map may retain a prior fix. Recorder timestamp checks prevent re-recording the same old fix as a new measured point.

**Caregiver phone location denied:** caregiver subscriptions are started independently of their own location bootstrap. Their own-position marker is missing, but permission denial is not the authorization gate for viewing the paired navigator's remote track. Internet/backend/Firebase access and navigator consent are still required. This is verified control flow, not a two-phone permission test.

**Internet lost:** phone track points remain queued locally and retry later. The caregiver sees only the latest uploaded point, a last-known/saved state, or an API error. Restarted local recordings are loaded as interrupted rather than silently represented as ongoing. No replacement position is invented.

## Gaps and any proposed source change

1. No firmware/GNSS acquisition implementation, BLE/serial/MQTT receiver or mobile telemetry sender was found in inspected first-party application source/dependencies. Bluetooth icons are not transport evidence. The backend accepts optional latitude/longitude but does not establish which hardware produced them; it currently stores no GNSS accuracy/fix-quality field for cane coordinates.
2. Two phone pipelines exist, and the caregiver map reads only breadcrumbs. A visible local route or successful `phone_location` update can coexist with an unavailable caregiver track if recording/upload failed. Legacy phone publishing uses a new **server publication timestamp**, not the original Position timestamp, and can republish a cached local fix on state/error notifications. This does not currently feed the caregiver map, but would be unsafe to treat as fresh measured GPS if that channel were adopted later.
3. Local `hasLiveFix` means non-null, not independently fresh/accurate. Permission errors can leave an old local marker. HTTP polling, 10s outbox retries, resetting patient subscriptions on connection-list updates and independent device clocks affect perceived freshness; no end-to-end latency or disconnect test has been performed.
4. Previous catalog inspection found no v2 tables in the configured database; pending migrations, patient-table selection, restricted database credentials, Firebase Admin configuration and deployed rules remain rollout blockers. That inspection was from the preceding backend audit, not a fresh production deployment check in this turn. No direct access to live navigator/caregiver location records was used here.

**Proposal only, before any source change:** if cane-first tracking is required, first confirm a cane GNSS receiver/antenna and firmware that supplies real WGS84 fixes, UTC sample time, fix validity and accuracy, plus a working uplink (independent network connectivity or an explicitly designed phone gateway). LiDAR alone does not supply global latitude/longitude. Provisioned credentials, assignment discovery, monotonic sequence handling, clock synchronization, reconnect/offline behavior and device power requirements must be verified. A phone gateway must relay authenticated cane-origin data without substituting phone coordinates or exposing firmware secrets.

Then introduce an explicit, tested source-selection policy shared by Track and the data card: show source/device ID/original fix time/accuracy, accept only fresh valid assigned-cane fixes, and allow phone fallback only under a stated product policy with a visible source change. Tests would cover cane disconnect, stale/invalid GNSS, denied phone permission, gateway/network loss, multiple assigned canes, clock skew, transfer and revoked caregiver consent. **No such change is implemented or approved by this inspection.**
