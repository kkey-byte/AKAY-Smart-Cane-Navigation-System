## Data lifecycle and ownership

| Data | Create / read | Update / delete and relationships |
|---|---|---|
| Firebase account + `Users` | Firebase SDK authenticates; `auth.register` inserts backend profile using verified token UID/email. `auth.login` selects by token UID. `requireProfile` requires exactly one recognized backend identity. | `profile PUT` updates only the actor's account fields. No account/role-change/delete HTTP API exists. Firebase sign-out does not delete PostgreSQL records. Legacy Firebase-deleted users can remain in SQL; they cannot obtain a usable authenticated session, but retention/reconciliation remains an operator responsibility. |
| Patient profile | `profile GET/PUT` selects/inserts by `req.actor.id`; client `userId` does not choose another patient. Unique `user_id` means at most one profile per **selected** table. | Transaction locks Users before the profile merge; omitted health fields remain intact and explicit null can clear health fields. Both existing patient tables have FK/uniqueness but are separate datasets. No automatic merge/delete was attempted. Legacy account deletion cascades to patient profiles; medication relationships must be included in any future consolidation plan. |
| Invitations / consent | `invite` creates a random private digest-backed code; caregiver `redeem` creates a pending connection. Navigator `decide` accepts/rejects their own request. | `revoke` permits either participant and soft-revokes only that relationship. Expiry derives from database wall time; listing now performs no expiry UPDATE. Pair uniqueness, invitation row locks and advisory locks prevent duplicate requests and consumed-code reuse. Neither claiming a cane nor knowing a public UID grants caregiver monitoring access. |
| Physical devices / credentials | Operator-only `provisionCane` creates inventory plus distinct private claim and machine secrets; SQL stores digests. `claim` binds custody to a navigator after proof. | `assign`, `release`, `transfer`, `acceptTransfer` lock the device and maintain immutable device ID plus ownership/assignment history. Ending assignment or custody closes history; does not delete measurements. Rearming requires released inventory and physical operator confirmation, rotates machine credentials, and writes a private output file. No HTTP route provisions hardware or reveals its secret. |
| Phone sessions | `navigation.start` derives owner from token and requires that account's `phone_…` source; creates a PostgreSQL navigation session. `/active` selects actor only. | Start serializes per owner and now closes Active **and Paused** predecessors. `/live` and `/end` check ownership and also constrain the UPDATE by owner. Terminal sessions are not reopened. Distance/duration cannot regress through late updates. No physical cane is inferred from a phone source. |
| Cane readings | `hardware/ingest` verifies a separate machine credential, locks device/credential, resolves its current assignment and derives navigator attribution. | Sequence must advance; assignment ID and timestamp must be current; coordinates/battery/status/alert kind validated. Inserts and last-sequence updates share a transaction; replay rolls back. Historical rows survive transfer and replacement. No normal update/delete endpoint exists. |
| Cane alerts | `ingest` inserts alert from the same reading/device/assignment/navigator transaction. `snapshot` reads at most 50 alerts for the selected authorized navigator. | No acknowledgement, resolution, purge or push-delivery API exists. Old-owner alerts stay with the old navigator; new owners do not inherit them. Prepared composite FK prevents an alert being relabelled to a different reading owner/device. |
| Phone GPS / breadcrumbs (RTDB) | `LiveLocationService` publishes own `phone_location/{uid}`; `FirebaseBreadcrumbRepository` writes own `breadcrumb_trips/{uid}/{trip}` with indexed points. | Owner rules allow own update/removal; caregivers cannot subscribe directly. Backend Admin reads trips after SQL consent checks and rechecks before returning. Snapshot currently reads the latest breadcrumb trip, not `phone_location`; recording is needed for its phone preview. SQL/Firebase deletion is not a cross-store transaction. |
| Curated places | Public search reads `places` and optional configured geocoder; no user profile records returned. | Removed startup sample seeding. No place-management HTTP API. Existing accessibility claims/sample rows were not inspected or deleted; provenance requires review. |

Legacy `caregiverprofiles`, `devicelogs`, `pairings`, `patientmedication`, `routehistory`, `savedplaces`, `searchhistory`, `smartcanes`, and `soshistory` have **no current HTTP CRUD implementation**. They are stored legacy data, not evidence that their features are active. `001_pairing.sql` preserves physical UUID/serial identities and records reconciliation needs for legacy pairings/phone sessions; it deliberately does not import old pairing status or `registered_user_id` as proven consent/custody. Exact legacy FK/delete actions are in the metadata artifact. Nothing was purged.

## Authorization findings

Verified in synthetic HTTP/SQL tests: raw UID-as-token is rejected; supplying another user's ID cannot select/edit their profile or end their session; caregivers cannot create navigator invitations; foreign custodians cannot release/assign devices; pending/rejected/revoked consent cannot authorize a snapshot/trip. Two navigators/two devices remain separate. Revocation **during** a mocked Admin trip read causes the final permission check to discard the fetched data and return 403.

`verifyFirebase` calls Admin `verifyIdToken(token, true)`; `requireProfile` checks current SQL role and ambiguous identity. `authorize` permits the navigator themselves or a caregiver with accepted active consent. `snapshot` and trip routes check authorization again after reads. This defines access at the final check; it cannot erase already delivered data or guarantee a response is recalled if consent changes afterward. Live Firebase Admin credentials, actual revoked tokens and production security rules were not tested. See [identity middleware](C:/Users/Asus/app_mobile/backend_patch/middleware/identity.js) and [v2 routes](C:/Users/Asus/app_mobile/backend_patch/routes/pairing.js).

There is no per-end-user PostgreSQL RLS model: the trusted shared backend credential can query the tables. Application requests are scoped by verified actor/consent, not by a client-controlled database session variable. The proposed runtime role reduces SQL capability, but still needs backend-wide SELECT and is not a replacement for HTTP authorization or secret protection. RTDB rules establish Firebase UID ownership, not the PostgreSQL navigator role; a Firebase-authenticated user can write their own phone/trip records even before backend profile completion. These are self-reported phone coordinates, not attested hardware readings. Strict navigator-role enforcement in direct RTDB writes would require a reviewed server-managed claims/write-proxy design.

## Confirmed issues fixed or prepared

1. **Implicit schema changes and ambiguous patient storage.** Normal `ensureUsersTable`, `ensurePatientProfilesTable` and `ensurePlacesTable` now validate catalog metadata only. `schemaCatalog.resolveTable` uses fixed identifier allowlists, verifies required columns and unique ownership/identity keys, and rejects ambiguity. Explicit `AKAY_PATIENT_TABLE` selects the approved patient table. Development bootstrap remains opt-in; production refuses it. Silent schema/uniqueness failures are no longer treated as success. See [schemaCatalog](C:/Users/Asus/app_mobile/backend_patch/database/schemaCatalog.js).
2. **Fabricated catalog data.** Removed all automatic “accessible” sample-place inserts. Empty inventory stays empty. Existing rows remain for human provenance review.
3. **Expiry after lock waits.** `redeem`, `decide` and `acceptTransfer` check database `clock_timestamp()` after relevant locks, including subsequent advisory/device locks. Transaction-start time can otherwise remain valid after real expiry. Lifecycle writes use database wall time; migration002 changes new assignment/ownership/received/alert/transfer timestamp defaults to wall time. Hardware freshness now uses the database clock rather than assuming Node and DB clocks match.
4. **Latest reading order.** `snapshot` now orders by measured `sampled_at`, then receipt time. An older sample arriving later no longer replaces a newer measurement. No missing reading becomes a zero location/battery.
5. **Validation/coercion.** Shared `validateProfile` rejects arrays, object-valued fields, booleans as age, conflicting aliases, impossible/non-ISO birthdates, overlong fields and insecure photo URLs before SQL. Registration uses it too; login rejects unrecognized stored roles and auth replies are non-cacheable. Existing partial-update semantics remain. See [validator](C:/Users/Asus/app_mobile/backend_patch/middleware/validateProfile.js).
6. **Session consistency.** Starting now closes Paused sessions as well as Active. Updates include owner in the SQL WHERE, reject unsupported live status, and preserve cumulative distance/duration against late smaller values. Legacy null numeric output remains unknown instead of becoming zero.
7. **Database invariants — prepared, not deployed.** Migration002 adds credential/device and alert/reading composite FKs, role/custody/identity guards, consent-state and time-order checks, nonnegative sequence and duplicate-alert protection. Existing inconsistent records cause full transaction rollback, not guessed reassignment/deletion. Established role or non-null Firebase UID changes require an explicit reconciliation procedure.
8. **Query efficiency.** Connection polling no longer writes expired rows. Prepared indexes cover latest measured sample, navigator alerts, active assignments, caregiver lists and owned devices. Migration001 reuses an existing valid UID unique index instead of adding a duplicate. No real-data EXPLAIN/load benchmark was run. Full breadcrumb paths still travel through Admin and HTTP on periodic reads; pagination/summaries and background polling suspension remain work. Rate-limit/audit/reading retention is not yet implemented.
9. **RTDB validation — prepared rules.** Phone timestamps must be numeric and recent, unknown fields are denied, and optional metrics are bounded. Trip start cannot be relabelled; points cannot predate it, and end dates cannot be arbitrarily future. Owner deletion remains allowed. Rules are tested in demo emulator only.
10. **Overprivileged database role — prepared cutover.** Migration003 creates a NOLOGIN runtime group without superuser/RLS bypass/role-creation capabilities, limits column updates to account/profile/session data actually edited, and grants no normal history deletion or schema DDL. It does not modify current credentials or automatically demote the existing service role. See rollout plan.
11. **Birthdate timezone and age consistency.** The installed driver parses SQL DATE as a JavaScript Date. [dateTypes.js](C:/Users/Asus/app_mobile/backend_patch/database/dateTypes.js) now preserves calendar-date text so profile responses retain `YYYY-MM-DD` through JSON and Flutter parsing. Profile reads/saves derive age from a known birthdate; manually entered age is used only when birthdate is unknown. Regression tests round-trip an exact birthdate without modifying stored dates or legacy timestamp interpretation.

## Remaining blockers

Approval and operator configuration are required to apply migrations, choose a patient table, and switch away from the superuser connection. Neither existing patient table can be called canonical from catalog metadata alone. Copying source does not apply SQL or restart a service; the next startup will deliberately refuse ambiguous patient storage until explicitly configured. V2 tables are absent from the configured database, so live pairing/telemetry cannot be claimed working.

Legacy navigation/device/history tables use `timestamp without time zone`; existing meaning is unknown. No automatic UTC conversion was attempted. New v2 timestamps use `timestamptz`. Age is derived at response time when birthdate is known; an age recorded without a birthdate can still become stale. No stored-date backfill was applied. Real row consistency, dataset size, query plans, deployed proxy/TLS/DB network restrictions and credential permissions require operator evidence or an authorized staging copy.

No account deletion/retention cascade workflow, alert acknowledgement/delivery, hardware attestation, distributed limiter cleanup or cross-store deletion transaction exists. Legacy cascading deletes and new restrictive historical FKs require an explicit retention plan before deleting users. Private provisioning files and SQL commits cannot be atomically committed together; an uncertain commit requires operator reconciliation and credential rotation, not automatic reuse of the output. Real Firebase tokens, production rules, two-device behavior and physical sensors remain unverified.
